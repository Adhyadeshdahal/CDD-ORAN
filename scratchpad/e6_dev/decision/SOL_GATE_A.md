# E6 Gate A adjudication

**Verdict: predeclared KILL for the frozen `E6-scn-v1` strong-SLA route with these xApps.** `DECISION.md` requires TS or TS+MRO ≤0.85× freeze *and* ≥35% removable SVR at **both loads of at least one** stress scenario. `GATE_A_RESULT.txt` has TS/TS+MRO ≈1.00–1.03× freeze and measured static/subset controllable fraction 0.017–0.099 throughout. Neither scenario passes even one load. Do not reinterpret the bar, pick a favourable seed, or call a subsequent oracle result a Gate A pass. Retain E6 as the negative/control result and pivot the primary contribution to headroom by action class plus constrained/Pareto control, with the real write/churn budget and guardrails. Do not claim an SLA edge from a privileged oracle.

**This is not proof the stress scenarios or the MLB/MRO problems are invalid.** The frozen implementation fails its *own* benchmark requirement: TS alone never improves eMBB violations versus freeze, including surge; MRO improves RLF only in mistune, while HO/ping-pong worsen and SVR does not improve. A weak actuator policy is a plausible cause of the failed intended positive control. The hindsight-tuned static improvement (2–11%) shows some headroom, but is neither a global optimum nor evidence that a WG3 controller can achieve 35%. Thus label the result precisely: *the current E6+xApp stack cannot support the preregistered SLA claim*. Calling it “benchmark invalid” and silently repairing it would erase a valid negative result; calling all of E6 fundamentally uncontrollable would overstate the evidence.

**A new version is legitimate as a separate experiment, not a rescue of v1.** Permit `E6-scn-v2`/a versioned xApp stack if the redesign is motivated by external 3GPP/O-RAN MLB/MRO behavior and an independently specified mechanism: e.g. TS measures neighbour load and border-UE feasibility, requests bounded CIO/HO changes toward genuinely spare capacity, and protects HO/RLF; MRO can address the actual mis-set Hys/TTT rather than only compensating with CIO. First audit proposal→quantization→ACK→realised changes and metric timing to identify a defect, with mechanical/unit tests and cited rules. Specify the algorithm, knobs, thresholds, budgets, scenarios, goals, guardrails, comparators, and **unchanged or explicitly new Gate A/B thresholds before any v2 SLA outcome**. No tuning on the five inspected DEV seeds, surge placement, mis-tune cluster, or observed failure ratios. Use distinct, registered fresh DEV seeds for v2 development and a further untouched confirmation/TEST set; paired arms on identical tapes, both loads, original base control. Re-run *all* Gate A arms (including freeze, noarb, TS, TS+MRO, subsets and tuned static) under the new stack and the same predeclared rule; only then consider Gate B. Publish v1 failure and every implementation/scenario change, and show v1/v2 side by side on fresh tapes. If original seed 11–15 results inform the fix, they are development evidence, never confirmation. A v2 pass is a new, narrower claim, not retroactive validation of v1.
